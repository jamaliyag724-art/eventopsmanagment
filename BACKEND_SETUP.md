# Utsav Backend Phase 1 — Vercel + PostgreSQL + Prisma

This phase adds the secure backend foundation while leaving the existing Utsav visual system and dashboard layout intact.

## Architecture

- **Hosting/runtime:** Vercel Node.js Functions through TanStack Start + Nitro.
- **Database:** PostgreSQL. Neon is the recommended managed provider to pair with Vercel, but any reachable PostgreSQL provider can be used.
- **ORM/migrations:** Prisma ORM 7 with the PostgreSQL `pg` driver adapter.
- **Authentication:** Better Auth email/password with database-backed sessions.
- **Organizations:** Better Auth Organization plugin with owner, admin, manager, and member roles.
- **Tenant boundary:** the active organization is derived from the verified Better Auth session; server helpers verify membership before any tenant data access.

Vercel is the application host, not the PostgreSQL database itself. A PostgreSQL database still has to be provisioned and its connection URLs added to the app.

## Runtime requirements

This project is pinned to **Node.js 24.x** in `.nvmrc` and `package.json`. Use the same Node 24 runtime locally and in the Vercel Project settings.

The Vite configuration explicitly selects Nitro's `vercel` preset when the build runs in Vercel. This is important because the Lovable wrapper's local default is Cloudflare, while the Prisma PostgreSQL TCP adapter needs the Node.js runtime.

## 1. Install the dependencies

The direct Zod dependency is pinned to the patched `4.6.7` line for GHSA-mrhx-c7xc-m3w5. The Events input schema uses Zod APIs compatible with v4. Regenerate `package-lock.json` locally with the install command below and commit it after validation.

The current npm audit also reports a Picomatch ReDoS advisory affecting versions through 4.0.7 in the TanStack/Vite toolchain. The advisory has no published fixed version at the time this package was prepared. Do not force-downgrade TanStack Router or add an unverified Picomatch override; re-audit when an upstream patched dependency is published.

After copying this backend update into the GitHub clone:

```bash
nvm install 24
nvm use 24
node -v
npm install --legacy-peer-deps
npm run db:generate
npm run db:validate
npm run typecheck
```

`npm install` updates `package-lock.json` for the new dependencies. Commit that updated lockfile with the code changes. Do not use `npm ci` until the lockfile has been regenerated by `npm install`. If npm reports the peer-dependency resolution issue previously seen in this repository, retry with `npm install --legacy-peer-deps` and use the same install setting in Vercel.

## 2. Provision PostgreSQL

Create a PostgreSQL database. Neon through the Vercel Marketplace is a convenient option; use its pooled URL for app requests and its direct URL for migrations.

Copy `.env.example` to `.env` and set:

- `DATABASE_URL`: pooled PostgreSQL URL used by the Vercel runtime. For Neon, use the pooled/`-pooler` hostname.
- `DIRECT_URL`: direct PostgreSQL URL used by Prisma migrations and schema tooling.
- `BETTER_AUTH_SECRET`: a random secret of at least 32 characters.
- `BETTER_AUTH_URL`: the exact local or production origin, without a trailing slash.

Generate the auth secret with:

```bash
openssl rand -base64 32
```

Never prefix secrets with `VITE_`. Those variables are bundled into browser code.

If your database provider supplies only one PostgreSQL connection URL, it is acceptable to use that same URL for both `DATABASE_URL` and `DIRECT_URL`. A pooled URL is preferred for runtime traffic; a direct URL is preferred for migrations.

## 3. Create the initial database schema

Once `.env` contains a real `DIRECT_URL` or `DATABASE_URL`, run:

```bash
npm run db:validate
npm run db:generate
npm run db:migrate:dev -- --name init
```

This creates the first Prisma migration under `prisma/migrations/` and applies it to your development database. The schema uses composite tenant-aware foreign keys for required event/vendor/workforce/sponsor/resource/workshop relationships; optional event/vendor/venue links are validated by server logic. Commit the generated migration directory. Do not run `migrate dev` against production.

Then run the existing routing tests and production build:

```bash
npm run test -- --run
npm run build
```

For production after the migration has been committed and deployed:

```bash
npm run db:migrate:deploy
```

Run production migrations deliberately before or as part of a controlled release. They are intentionally not run automatically during `vite build`.

## 4. Configure Vercel

In Vercel → Project → Settings → Environment Variables, add these values for the environments you intend to use:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Pooled PostgreSQL URL |
| `DIRECT_URL` | Direct PostgreSQL URL |
| `BETTER_AUTH_SECRET` | Output of `openssl rand -base64 32` |
| `BETTER_AUTH_URL` | Your exact production URL, e.g. `https://your-domain.example` |

Also set Project → Settings → General → Node.js Version to **24.x**. Redeploy after changing environment variables. Do not deploy this backend code until the production database has been migrated and all four environment variables are present; otherwise protected routes and auth endpoints will fail until the database is ready.

For Vercel preview deployments, set `BETTER_AUTH_URL` to the relevant preview origin if you need authentication to work on that preview. `VERCEL_URL` is also added as a trusted origin for the current Vercel deployment hostname.

## 5. Verify the backend

Start locally:

```bash
npm run dev
```

Then check:

- `GET /api/health` — verifies PostgreSQL connectivity without exposing credentials. It returns HTTP 503 until `DATABASE_URL` is set and migrations have been applied.
- `/signup` — creates a Better Auth account and an initial organization.
- `/login` — authenticates and activates the user's first organization membership.
- `/app` and `/app/:module` — require an authenticated user with an active organization.
- `/admin` — requires `User.platformRole = "PLATFORM_ADMIN"`.

The initial sign-up flow creates a workspace with the user as its owner. The first login currently selects the first organization returned for that user. A proper organization switcher is a later integration task; the existing sidebar's sample organization selector is still demo UI.

## 6. Promote the first platform administrator

Platform admin access is not self-assignable during signup. After creating your own user account, run this SQL in your PostgreSQL console, replacing the email with your intended platform-admin account. Email verification is not configured in this phase:

```sql
UPDATE "user"
SET "platformRole" = 'PLATFORM_ADMIN'
WHERE email = 'your-admin-email@example.com';
```

Do not expose this operation as a public API.

## What is real now, and what is still demo data

Implemented in this phase:

- PostgreSQL Prisma schema for Better Auth, organizations, events, tasks, vendors, expenses, workforce, sponsors, venues/resources, workshops, documents, and audit logs.
- Better Auth API route, email/password signup/sign-in, organization creation, organization membership, and session cookies for TanStack Start.
- Protected `/app`, `/app/:module`, and `/admin` route entry.
- Tenant context helper that derives the active organization from the session and verifies membership.
- Tenant-scoped `listOrganizationEvents` and `createOrganizationEvent` server functions, including role check and audit record for event creation.
- PostgreSQL health endpoint.

Still to implement in later phases:

- Connect each dashboard module's current mock arrays and local-state forms to the Prisma server functions. The UI is intentionally not redesigned in this backend foundation phase.
- A real organization switcher, team invitations, invitation email delivery, and organization settings workflows.
- Email verification, password reset emails, email provider, and production-grade rate limiting/abuse monitoring. Password signup is enabled without email verification in this initial integration; do not treat an email as verified until the mail flow is implemented.
- File upload provider/storage policies, real notification delivery, subscriptions/payments, and background jobs.
- PostgreSQL Row-Level Security policies. Until those migrations are added and tested, every future data access must use the verified tenant context and include `organizationId` in all tenant-scoped Prisma filters. Do not write unscoped queries against tenant models.
- Dedicated integration tests against an isolated PostgreSQL database, cross-tenant access tests, backup/restore verification, and production security review. The schema and helper layer reduce tenant-mixing risk, but database Row-Level Security is still a required defence-in-depth phase before handling real customer data.

This is a real backend foundation, not yet a finished production SaaS. Do not enable real customer data or billing until the remaining security, email, RLS, and module-integration work is complete.
